# Changelog

All notable changes to **Tadah.CORE** are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
versioning follows the umbrella project (Tadah.MLIP).

## [Unreleased]

### Added
- Tests: `tadah.core_headers` (`ctest -L headers`, cmake-tools' `tadah_add_header_check`) compiles every header of `include/` and the generated `blueprint_tadah.hpp` on its own and twice in a row, with what a user of `tadah.core` gets. Every CORE header passes.
- **`parse_one_based_indices(values, total, who, counted)`** (`utils.h`): the checked 1-based index list of `parse_dataset_indices` (the same grammar and refusals; the bounds are checked before a range is expanded), whose bound message ends with `counted`, what the indices count: `tadah analysis bfunc: index 9 (in '2-9') is outside 1-4 (the D2_Blip basis has 4 functions)`. `parse_dataset_indices` is now `parse_one_based_indices` with `the dataset has <N> structures`; its messages are unchanged. `tadah data print`, `analysis descriptor` and `analysis bfunc -i` use them (see Tadah.MLIP). The lenient `parse_indices` stays for `FIXINDEX`, its only remaining user.

### Changed
- `INDEX` descriptions: the general text states the strict rules (1-based, within the items selected, a descending range, a step of 0, a malformed or empty entry and an index outside refused; it said only that repeated indices are removed), and `data print`, `analysis descriptor` and `analysis bfunc` have their own: the structures to print or analyse, and for `bfunc` the basis functions of the descriptor (it inherited the text about dataset indices).
- `TASK` description: options above the first `TASK` line apply to every task, a `TASK` line with no parameter lines runs with those alone, and every task name is checked, with or without parameters, a command that needs a subcommand (`TASK data`) included (Tadah.MLIP's task-file parser dropped a `TASK` line without parameter lines, unchecked).
- `EAMFAST` description: the speed-up and the log line it quotes are given for a D2_LJ potential (`RCUT2B 6.5`, `Cut_Dummy`), which they were measured with, instead of for the docs quickstart potential, which is now a D2_Blip + DM_mBlipEnv model that runs the generic kernel (see Tadah.MLIP). It also names DM_REAM as the only many-body descriptor for which the EAM collapse is implemented: a model with any other many-body descriptor (DM_mBlipEnv, for example) runs the generic kernel; the description used to say "many-body descriptors that are not EAM-form".
- Blueprint: `OALGO` says what options 2 and 4 refuse before LAPACK runs (fewer data rows than weights; with `LAMBDA > 0`, fewer than the intercepts), where LAPACK stops (option 2 at an exactly zero diagonal element of R, option 4 at a Cholesky pivot that is not positive), and that a column that depends on others without being exactly a combination of them in floating point is still fitted by both, with very large weights; NaN or an infinity is refused under every option (Tadah.MODELS). `SETFL` says how the file is read (as LAMMPS `pair_style eam/alloy` reads it: lines 1-3 comments, then `#` comments and lines without words skipped, each table starting on a new line) and what a malformed file is refused for (Tadah.MODELS).
- Blueprint: `SIGMA` says what it holds (N, then the N×N covariance of the weights of an `OALGO 3` fit, M_BLR or M_KRR), that a fit replaces the `SIGMA` of its configuration and a fit that computes none writes none, and that `tadah predict --error` refuses one without N×N+1 values; it said "An N×N matrix in column-major order. Applies to M_BLR". `MPARAMS` says that the `Kern_Polynomial` degree is an integer (2.7 is refused), that `Kern_RBF` refuses sigma 0 and evaluates a negative sigma as its magnitude, and which `OPTIM MPARAMS` lines `tadah hpo` refuses at startup; it said the degree "is read as an integer". `SBASIS` says that `OPTIM SBASIS` is refused (see Tadah.MODELS and Tadah.HPO).

### Fixed
- **An assignment to a column of an `fd_type` or an `aeds_type2` writes into it.** A column is an `aed_type` view of its container's values; `fd[k] = v`, `fd(k) = v`, `aeds[c] = v` (a copy or a move, `fd[k] = a * 2.0` included) now write `v`'s values into the container, which `fd(i, k)`, `ptr()` and a copy of it read, and the column stays the view. The assignment made the column own a new buffer with the values: the container kept its old values, so `D2_Base::calc_fd_approx` (`fd(0) = ...`) wrote nothing into its `fd_type` (Tadah.MODELS). A vector of another size is refused (`std::invalid_argument`: `aed_type: cannot assign 4 values to a view of 3 values (a column of an fd_type or aeds_type2 is a view of its values)`; it replaced the column), and a view is not resized to another size. Moving a column out (`aed_type x(std::move(fd[k]))`, `x = std::move(fd[k])`) copies it: it took the column's pointer and left the column null with its old size. `aed_type::rebind()` makes an aed_type a view and `is_view()` tells one; a default-constructed `fd_type`'s columns are empty views; an owning `aed_type` is assigned as before, and a moved-from one has size 0. Every assignment to an `aed_type` in the Tadah modules was checked (compiled with the operators deprecated): apart from `calc_fd_approx` and two test helpers, none assigns to a column. Test: `test_fd_type.cpp`, `test_aeds_type.cpp`.
- **A configuration key's examples are values of the key, and a refused value lists each once, after the key.** When CoreUserConfigParser refuses a value it lists the key's examples as `<KEY>   <example>`; 64 examples of 36 keys began with the key themselves, so the key was printed twice (`BETA   BETA 0.0001`, `RCUT2B   RCUT2B 3.0`), and an example of several lines (the D2_mJoin, DM_mJoin and grid examples) was printed as one message, whose later lines were the example's own text, without the `    <KEY>   ` and the log prefix (`[<time>] ERROR: `) in front: the line after `    CGRID2B   CGRID2B   1.0 2.0` read `CGRID2B   1.5 2.5`, and those after `    TYPE2B   TYPE2B    D2_mJoin` read `  TYPE2B    D2_MIE 11 6 Ti Ti` and so on. The examples are now values (`0.0001`), one per line for an example of several lines of the key, and each line is listed as `<KEY>   <value>`. IN_PLACE's example was its command-line flag, `--in-place`; it has TYPES.BOOL's, as the other switches. The `tadah refit` blocks INIT, EXPLORE, REFINE, FUSE and OPTIMIZER have no examples, since the text after the key on its line is not read: their descriptions show the layout (OPTIMIZER's example named a directory that is in no Tadah repository). A DM_mJoin example named the element pair `Ti TI`; it is `Ti Ti`. The blueprint's header states the rule, and the test of the examples checks it (it accepted an example that began with the key or its flag).
- **`fd_type`'s `+`, `-`, `isApprox`, `==` and `*` with a vector check their operands' sizes.** They looped over the size of the left operand (or of the vector) and read past the end of the smaller buffer when the other had fewer rows, and `==` called two fd_types of zeros of different sizes equal. Now `+` and `-` throw `std::invalid_argument` naming both row counts (`fd_type: operator- of fd_types of 4 and 2 rows`), `*` throws when the vector's size is not `rows()`, and `==` and `isApprox` are false for fd_types of different sizes: one check per call, outside the loop. The element accessors `fd(i, k)`, `fd[k]` and `fd(k)` stay unchecked; their preconditions (`i < rows()`, `k < 3`) are documented. The test `fd_type out-of-range checks` asserted nothing in any build (`REQUIRE(true)`, or a `WARN` under `NDEBUG`) and is replaced by `fd_type: operations on fd_types of different sizes are refused` and `fd_type: operations on fd_types of one size are elementwise`. The whole suite passes with the checks in place (the force predictions of `BF_Linear` and `Kern_Linear`, `fdij * weights`, among them).
- **A default-constructed or moved-from `fd_type` has three empty columns.** `fd[k]` and `fd(k)` dereferenced its null column pointers (a segmentation fault), although it has `rows()` 0, as `fd_type(0)` has, whose columns are empty. The columns are now views held by value, so `k < 3` is the whole precondition of the column accessors, and a sized `fd_type` no longer allocates three column objects on the heap; `operator<<` still prints nothing for an `fd_type` without storage. Tests: `fd_type: a default-constructed fd_type has three empty columns` and `fd_type: a moved-from fd_type has three empty columns`.
- **`Context::get(key, container)` refuses a key that stores more values than the container holds**, naming the key and both counts, before it writes an element (`Context::get: key SIGMA stores 34 values, but the container it is read into holds 17`), and logs an ERROR. It wrote every stored value, into a `std::vector` past its end: MODELS' `read_sigma`, which sizes its buffer from the first `SIGMA` value, so corrupted the heap with a `SIGMA` that a second fit had appended to (`tadah predict --error` aborted). A key with fewer values than the container holds fills those and leaves the other elements as they were, as before; the docstring said a warning was logged for more values. Test: `test_context.cpp`.
- **An integer read of a configuration value takes an exact integer only.** `get<int>()`, `get<size_t>()` and the other integer types (bool and the character types excepted), the n-th value and `get(key, container)` into integers take the whole token when it is a decimal number whose value is an integer in the range of the type, whatever its spelling (`2`, `+2`, `2.0`, `2.`, `1e3`, `.5e1`); the value is computed from the digits, independently of the locale. A fraction (`2.7`, `1e-3`), trailing text (`2abc`, `1e`), a value out of range (`3000000000` for `int`, `-1` for `size_t`) or text that is not such a number (`0x10`, `inf`) is refused, naming the key, the value and the range (`Conversion failed for key=MPARAMS, value="2.7": an integer is required, from -2147483648 to 2147483647`). They read the integer prefix of the text without an error: `MPARAMS 2.7` gave the `Kern_Polynomial` degree 2, `1e3` gave 1, `2abc` gave 2, and a `size_t` `-1` gave 18446744073709551615. Reads of strings are unchanged (floating and bool reads: the next entry). Test: `test_context.cpp`.
- **A floating or bool read of a configuration value takes the whole token.** `get<double>()`, `get<float>()`, `get<long double>()`, the n-th value and `get(key, container)` into floating types take the token when it is a decimal number with a finite value in the range of the type, in any decimal spelling (`1`, `1.5`, `.5`, `5.`, `+2`, `-1e-3`; a subnormal such as `1e-310` reads as before) (`parse_decimal_finite()`, with float and long double overloads, and `is_decimal_literal()`, `number_format.h`). Trailing text (`1.5abc`, `1.5.2`), text that is not a decimal number (`0x10`, `abc`, an empty token), a value that is not finite (`inf`, `nan`, `1e400`) and a `float` out of its range (`1e39`) are refused, naming the key and the value (`Conversion failed for key=MPARAMS, value="1.5abc": a finite decimal number is required`). A bool read takes `true` or `false`, the whole token (`truex` is refused: `true or false is required`). The reads used `std::istringstream` and took the numeric prefix without an error: `1.5abc` and `1.5.2` were 1.5, `0x10` was 0, `1.0,2.0` was 1, `truex` was true; the other refusals gave no reason. A configuration line is checked against the key's blueprint type when it is parsed (the `DOUBLE` pattern refuses `1.5abc`, `inf` or `nan`), but the pattern of a list key (`{DOUBLE}`) takes a comma or a `+` between two values, which the parser does not split at, and a line of 2048 characters or more skips the patterns (a numeric shortcut that also takes commas as separators and accepts `inf`, `nan` and hex numbers). So, on a line of any length, `MPARAMS 1.0,2.0`, `FIXWEIGHT 0.1,0.2`, `CGRID2B 1.0,2.0,3.0` and `SGRID2B 1.0,2.0 3.0` were stored as the tokens `1.0,2.0` (and `3.0`) and so on, and read as 1.0, 0.1, 1.0 and 1.0, the first number of each token, without an error; they are now refused when the key is read (`Conversion failed for key=FIXWEIGHT, value="0.1,0.2": a finite decimal number is required`), and the parser still accepts the line. The other prefixes (`1.5abc`, `0x10`) reached the reads only from values that programs store in a `Context` (C++ callers, potential files they write) and from lines of 2048 characters or more. Test: `test_context.cpp`.
- **A `CONFIG` line with an inline comment** (`CONFIG config.train   # nested config`) includes the file it names. The parser kept the blanks before the `#` in the line, so the path was `config.train   `: `tadah train -c`, `tadah --task` and every other reader of such a file stopped with `Failed to open config file: config.train   `, and an include chain that was circular reported that error instead of the chain. The blanks before an inline comment are now dropped from every key line. Other keys were not affected: their values are read as whitespace-separated tokens. (The `TASK` lines of a task file are read by Tadah.MLIP, which now ignores their comments too.)

## [1.6.0] — 2026-09-25

### Added
- **`Matrix3d * Matrix3d`**, the row-by-column matrix product.
- **`parse_dataset_indices(values, total, who)`** (`utils.h`): the checked 1-based structure indices of `tadah data sample` and `data balance -i`. The values form one list (entries separated by commas or whitespace, spaces allowed around `-` and `:`), repeated indices are removed, and an empty entry, a token that is not an index, a descending range, a step of 0 and an index outside 1 … total are refused, naming the text; the bounds are checked before a range is expanded.
- **`CoreUserConfigParser::refuse_keys({key → reason})`:** a line that sets a refused key, in any letter case and in a `CONFIG` include too, is an error naming the key, the line, the file and the reason (`Key FORCE on line 2 of val.tadah is not accepted here: …`). HPO's `--validation` file refuses `FORCE` and `STRESS` this way.
- Strict index parsing for indexed configuration keys.
- Blueprint field `allowed_values` (`BlueprintKey::allowed_values`, `isAllowedValue()`): the only values of a single-string key, matched without regard to case. `BlueprintParser::buildKey` requires a non-empty list of non-empty strings on a `STRING` key with `value_N = [1]`, and the key's default and examples among them. `CoreUserConfigParser` rejects another value at the line that sets it, naming the file (`Invalid value for key EMBF0 on line 3 of pot.tadah: 'ZEROO' (allowed: ZERO, FREE)`; lines that come from no file give the line alone), and `validateWithBlueprint` (the CLI and task path) refuses it with an `Allowed values` log line; `validateSchemaOnly()` is the type check alone. `EMBF0` is the first key that uses it (`value_format` `ZERO|FREE`). Test: `test_blueprint_allowed_values.cpp`.
- Deprecated configuration keys: the blueprint field `deprecated` holds the reason and the replacement. `CoreUserConfigParser` accepts a deprecated key, checks its value against the key's format, writes one notice per key and process to standard error (`WARNING: Deprecated key MBLOCK is ignored: …`, through `report_ignored_key_once`, however many lines, `CONFIG` files or parses read it) and does not store it. The notice bypasses the `Logger`, so neither the log level nor a `VERBOSE` line suppresses it, and `pair_style tadah` in LAMMPS (which leaves the `Logger` at `ERROR`) shows it too. `BlueprintParser::buildKey` rejects a deprecated key with a `default_value` (`Context::contains()` would insert it, and it would reappear in every written potential), a CLI flag or examples (the configuration-keys page and the invalid-value error would show how to use it; `examples = []` overrides those of an inherited `TYPES` table), and `findClosestKey` never suggests one.
- `EMBF0` key (`ZERO` | `FREE`, default `ZERO`): the DM_REAM embedding reference (see Tadah.MODELS). It takes `ZERO` or `FREE` only, in any case (`allowed_values`, below); any other value is an error at its line. STRING key with an explicit blueprint default, so the DM_REAM constructor materialises it into the model Context and every DM_REAM potential is written with an explicit `EMBF0` line. `refit_constrain_f0` description: effective under `EMBF0 FREE` only.
- **BREAKING — `RHOFORM` key (`SIGNED` | `NONNEG` | `MONOTONE`): the DM_REAM density form (see Tadah.MODELS), mandatory and without a default.** A STRING key deliberately given no `default_value`: every DM_REAM potential and configuration must declare it, and nothing supplies it implicitly. Readers go through `Context::has_stored()` / `stored_value()` only (a `Context::get` on the absent key would log a spurious ERROR before throwing). Its `allowed_values` are `SIGNED`, `NONNEG` and `MONOTONE`, in any case (`value_format` `SIGNED|NONNEG|MONOTONE`): another value is an error at its line, naming the file, as for `EMBF0` (`Invalid value for key RHOFORM on line 24 of pot.tadah: 'SQUARE' (allowed: SIGNED, NONNEG, MONOTONE)`), also in a potential without a DM_REAM block. The `AMPGRIDMB` description says what the amplitudes multiply under each form, and the `refit` task text lists `RHOFORM` as a required refit key. Test: `test_blueprint_allowed_values.cpp`. **Migration:** add `RHOFORM SIGNED` to a DM_REAM potential or configuration written before tadah 1.6.0 to use it unchanged. Binaries older than the key refuse a potential that carries it (`Invalid key: RHOFORM`).
- `number_format.h`: lossless number text. `format_roundtrip()` gives the shortest text that reads back as the identical double (`std::to_chars`); `format_sig()` / `format_sig_chars()` give locale-independent `%.{N}g` (a finite value never renders to text that overflows); `reformat_double_token()` re-renders one token; `to_double()` / `parse_number()` parse like `std::stod`, except that an underflowing literal is a value (the subnormal or ±0) rather than an error; `resolve_pot_digits()` / `pot_digits_warning()` implement the potential-file precision rule below.
- `to_string_lossless()` (`utils.h`) for scalars, strings and ranges. `to_string(x, n)` is for human-facing text only.
- `Context::has_stored()` / `Context::stored_value()` look a key up without inserting its blueprint default.
- `IUserConfigParser::parse(lines, first_line, source)` (implemented by `CoreUserConfigParser`): parses lines taken out of a larger source, such as the `TASK` section of a task file, where `lines[i]` is line `first_line + i` of `source`, so that an error that names a line names the line of the file, and the file (`Invalid value for key EMBF0 on line 6 of run.task: 'frei' (allowed: ZERO, FREE)`). MLIP's task-file parser uses it. A class that implements `IUserConfigParser` must implement it too (pure virtual). Test: `test_blueprint_allowed_values.cpp`.
- `Context::write_potential(os, sig_digits)`, the potential-file writer: the `operator<<` layout, never a NUMERIC line, and every non-integer number of a key with a DOUBLE position rendered with `sig_digits` significant digits; integers, strings, `LIN`/`GEOM`, bools, index patterns and inf/nan are written verbatim.
- `key_notice.h`: the notice of a key that is accepted but has no effect. `report_ignored_key(subject, reason)` writes `WARNING: <subject> is ignored: <reason>` to standard error in one insertion (not a `Logger` message, so neither the log level nor `VERBOSE` hides it, in LAMMPS either); `report_ignored_key_once(key, subject, reason)` writes it at most once per key and process (thread-safe), and `ignored_key_reported(key)` says whether it has. The deprecated-key notice of `CoreUserConfigParser` goes through `report_ignored_key_once` (the text is unchanged; once per key and process, as for every ignored key, by the owner's decision of 2026-09-29: parsing a potential with `MBLOCK 64` and `EMBF0 FREE` twice in one process prints each notice once); MODELS reports `EMBF0` and `RHOFORM` without a DM_REAM block through `report_ignored_key_once`, and the `EMBF0` and `RHOFORM` descriptions say so (they said a WARNING). Test: `test_key_notice.cpp`.
- `parse_decimal_normal()` (`number_format.h`): the number grammar of the hpotarget file, `parse_decimal_finite()` whose value is also zero or a normal double (a subnormal such as `1e-310`, and a nonzero literal that underflows to 0 such as `1e-400`, are refused; the tests are on the bits). HPO's `parse_number` reads hpotarget numbers with the same grammar, and MLIP's `tadah refit --retarget` reads its `--pct` and `--set` numbers with it, so every number it writes into an hpotarget is one `tadah hpo` reads back. Test: `test_number_format.cpp`.
- `RETARGET_RHOFORM` key, the `--rhoform SIGNED|NONNEG|MONOTONE` option of `tadah refit --retarget` (`allowed_values`; needs `--retarget`): the density form of the potential an hpotarget searches around, for a file written without the `RHOFORM` header line (see Tadah.MLIP). The `refit` help and the `retarget` key describe it, the `RHOFORM`/`EMBF0` rules of the `--edit` and `--retarget` configurations, and the checks on `--pct` and `--set` (the hpotarget number grammar, an `OPTIM` line on each `--pct KEY`, finite `--set` bounds within the density form's rule). The `analysis check_bounds` help says how each corner is built and that a DM_REAM seed must declare `RHOFORM`. Test: `test_blueprint_allowed_values.cpp`.

### Changed
- Blueprint: the keys of the non-linear models (MODELS and MLIP 1.6.0). `MPARAMS` lists each kernel's parameters (`Kern_RBF` sigma, with gamma = 1/sigma^2; `Kern_Polynomial` d gamma c; `Kern_Sigmoid` gamma c; the others none); it said only that some models take parameters. `MODEL` lists the kernels and basis functions and says what the third token of `M_KRR` selects (implementation 1, the least-squares fit of energies, forces and stresses, or 2, energies only). `SBASIS` says that it is required by a non-linear `M_KRR` kernel, that basis vector 0 is the bias vector e0 and the others are drawn from the training data by a fixed draw (std::mt19937_64, default seed 5489), its bounds (at least 2, at most the number of candidates plus 1), and that the potential records it with `BASIS`; it said "Number of basis functions for the DesignMatrix". `BASIS` says how the vectors are stored and which potentials are refused, and that `pair_style tadah` refuses a non-linear potential trained with `BIAS true` on several species (its descriptor has one bias component per species, the one tadah trains one shared component). `LAMBDA` says which columns of each function the penalty leaves out (the intercepts) and that `OALGO 3` refuses `LAMBDA != 0` for a model with one.
- **`Matrix3d` has no scalar `+=`/`-=`** (double or int), and its element-wise `+=`/`-=` templates no longer accept an arithmetic type: they added the number to all nine entries, which is never meant for a cell or a stress (the CASTEP `.md` reader's `s.stress -= p` shifted the shear components too). Code that used them does not compile; write `m(k,k) -= p` for each k.
- Blueprint: LSCALE divides stresses by the cube of the factor (the description said they are invariant); `tadah data dedup` describes how structures are matched, that comparing a structure with a singular cell is an error, the largest threshold, and that `--threshold` is required, and its examples pass it; `tadah data balance --rescale` says that a weight of 0 is kept; `tadah data sample` says that exactly one selection is required, what `--uniform` and `--random` select (every N-th structure from the first; N distinct structures drawn from the whole dataset, in dataset order) and that indices run from 1 to the number of structures, and its examples select something (the only one selected nothing and wrote an empty dataset); the `--index` of `tadah data sample`, `data balance` and `data write` says how its indices are checked (`parse_dataset_indices`); `tadah data merge` registers `-d` only in its input group, so its help example works (`-d` was also a plain key, and every command-line merge exited 106: `Exactly 1 option from [-t,--task,-d,--dbfile] is required`).
- Blueprint: `tadah predict --analytics` says which metrics it prints, that a structure with force or stress weight 0 is left out of the force or stress metrics, that a dataset whose structures all have that weight 0 is not measured (nan, left out of the mean), that with `-F` (`-S`) a run in which no dataset has the data is refused before predicting, as is a dataset the filters leave empty, and that the training-only weight keys a potential records are not applied.
- Blueprint: `CLOSE_CONTACT` (`--close-contact <A>`), the close-contact list of `tadah analysis dataset_stats`; its description says that r_min counts a pair at distance 0. `STRUCTURE` says how a CIF's space group (the symbol forms read, numbers 1 to 230, the monoclinic cell check) and occupancies are read, that AFLOW IDs (`aflow:<auid>`) are accepted, that a CIF structure's label names the space group its cell is built with and the errors and warnings of a COD entry its COD ID, and that a failed fetch from any database (MP, COD, AFLOW, NOMAD) gives the ID and the service's reason, cut to 300 characters.
- Blueprint: `SETFL` names the descriptors that read the file, D2_EAM (the pair function) and DM_EAM (the density and the embedding function), so one file serves both (DM_EAM now reads it; see Tadah.MODELS), says that their `TYPE2B`/`TYPEMB` parameter is the placeholder 0 (another value is reported as ignored) and that `RCUT2B` and `RCUTMB` must be the file's cutoff (another is refused; see Tadah.MODELS), and gives a configuration with both in its text. It said only "Path to the setfl file with the EAM potential." Its examples are setfl paths: the parser prints each example after the key when it refuses a value, so the configuration showed as `SETFL   INIT2B    true`. `SIGMA`'s example drops its backticks, which its format does not accept. Every example of a key is now a value of the key or a line that starts with the key or its command-line flag (`test_blueprint_parser.cpp`).
- Framework version bumped to `1.6.0` (`blueprint/blueprint_tadah.toml`), the single source every module's CMake `project(VERSION)` reads. The release carries exact number handling in potential and dataset files, a non-zero exit when the best potential cannot be saved, the DM_REAM zero-referenced embedding (`EMBF0 ZERO`) as the new default (**BREAKING**: add `EMBF0 FREE` to a 1.5.0 DM_REAM potential to reproduce its energies), and the mandatory DM_REAM density form `RHOFORM SIGNED | NONNEG | MONOTONE`, with no default (**BREAKING**: add `RHOFORM SIGNED` to a DM_REAM potential or configuration written before tadah 1.6.0, bit-identical); see the module changelogs.
- The blueprint is a CMake configure dependency: editing it (e.g. a version bump) re-runs the configure step, so the embedded blueprint and `tadah --version` can no longer go stale.
- The `0.0.0` fallback for a missing version reader is gone: an out-of-date cmake-tools is a configure error.
- Tests take Catch2 and its test discovery from cmake-tools (`tadah_setup_tests()`, `include(Catch)`). The vendored `tests/catch2/catch.hpp`, `tests/Catch.cmake` and `tests/CatchAddTests.cmake` are removed, and so is the test-local `Catch2` target, whose include directory did not exist.
- cmake-tools is fetched at `v1-dev` instead of `main`.
- The `EAMFAST` description says that each collapse table is certified when the potential is loaded (relative tolerance 1e-9 for the value and the derivative, the error of each table segment bounded from 31 check points), that the fast path evaluates the analytic function below the certified range, that a single failing segment (a basis knot, a switching-cutoff junction) ends that range, and what the LAMMPS log line reports. It claimed about 1e-9 relative accuracy at every distance and "typically 5-10x faster force calls"; it now gives measured speed-ups (1.6x to 4.5x in 250-atom MD runs, growing with the cost of the descriptors).
- The blueprint text of the `tadah refit` `OPTIMIZER` block (the `OPTIMIZER` key on the configuration-keys page and the stage-pipeline paragraph of `tadah refit --help`) lists the keys each stage reads and says that `ALGO` is required and any other key is an error, as `tadah refit` now enforces. It said the block took the stopping criteria of the `tadah hpo` `OPTIMIZER` block, `FTOL_ABS` and `XTOL_ABS` included.
- The same text says that `LIB` is required wherever the block runs an optimiser, naming the library of its `ALGO` (`NLOPT`, `DLIB` or `CERES`), that `LIB` with `ALGO NONE` is an error, and that `MAXEVAL` and `MAXITER` are integers from 1 to 2147483647, as `tadah refit` now enforces. It said `LIB` was needed only where the `ALGO` did not name the library.
- The same text says that `LIB` with `ALGO UNIFORM` is an error, as with `NONE`, and so is a stopping criterion in a block with `ALGO NONE` or `UNIFORM` unless another stage reads it, and that `MAXEVAL`/`MAXITER` counts the objective evaluations of the NLopt and dlib algorithms exactly and the iterations of Ceres' `LM` and `DOGLEG`, as `tadah refit` now does. It said `UNIFORM` did not check `LIB`.
- The same text says that the tolerances of a `tadah refit` stage block (`FTOL_REL`, `XTOL_REL`, `GTOL`) are finite numbers >= 0, as `tadah refit` now enforces (a negative one made Ceres return without iterating, so REFINE and FUSE did nothing).
- The same text says that FUSE reads `GTOL`, that its `MAXEVAL` bounds the whole stage under `REFIT_OBJECTIVE energy` and each function's FUSE refine under `REFIT_OBJECTIVE curve`, and no longer that REFINE's stop criteria with `ALGO NONE` are read in curve mode, as `tadah refit` now does; the `FUSE` key says what FUSE fits in each mode (it described the energy-mode joint refinement only).
- The same text, and the stage-pipeline paragraph of `tadah refit --help`, give the stopping criteria each `ALGO` reads and say that a key its `ALGO` does not read is an error, that `MAXITER` is the alias of `MAXEVAL` for Ceres' `LM` and `DOGLEG` only, that dlib's `LBFGS` reads `FTOL_ABS`, and that `ENABLED false` with an `OPTIMIZER` block is an error, as `tadah refit` now enforces. They said that a key the stage does not read is an error, and listed the stage's keys only.
- Blueprint: the `tadah refit` numbers state their ranges, as `tadah refit` now enforces before it reads the EAM file (Tadah.MLIP): `REFIT_TOL_AMBIENT`, `REFIT_TOL_COMPRESSED`, `REFIT_COMPACT_SHARE`, `REFIT_REACH_MARGIN`, `OUTPUT_GRID_SCALE` and `OPTIM_PCT` > 0 (`OUTPUT_GRID_SCALE`'s grid 3 to 2147483647 points per table), `REFIT_REACH_SMIN` from 0.1 to 1, `REFIT_R_LO_FRAC` in (0, 1), `REFIT_CURVE_DERIV_WEIGHT` >= 0, the compact counts from 1 (`REFIT_COMPACT_JITTERS` 0 to 2147483646), `REFIT_COMPACT_SEED` 0 to 4294967295, `N2B`/`NRHO_BASIS`/`NF_BASIS` 1 to 1024, `REFIT_MAX_ESCALATIONS` from 0, and the sample grid of `REFIT_COMPACT_NMAX`; `tadah refit --help` says the numbers are read strictly. `REFIT_CURVE_RELAX` no longer says it is rejected in energy mode (it has no effect there, and its value is checked).
- `Mat6R3C::row()` and `Matrix3d::row()`/`col()` return const copies. Assigning to one (`m.row(n) = v`, `m.row(n) += v`, `m.row(n)[k] = x`) compiled and changed the temporary copy instead of the matrix; it is now a compile error. `Mat6R3C::set_row()` writes a row. The MLIP `DIMER` descriptors were computed from a zero displacement matrix this way (fixed in MLIP 1.6.0). Test: compile-time checks in `test_maths.cpp`.
- The `DIMER` key's description says that a `DIMER` potential is evaluated with every atom as Z=1 (`tadah train`, `tadah predict` and `pair_style tadah`): every pair gets the weight of the Z=1 (H-H) pair, which is 1 unless `WATOM` sets one for H, not the `WATOM` weight of the potential's element. Its `TYPE2B`/`TYPEMB` descriptors must therefore be declared for `* *` element pairs, and a potential naming specific element pairs is refused when it is loaded (MODELS, MLIP and Tadah.LAMMPS 1.6.0).
- The README badges and links and the pointers to the umbrella's community files (`CITATION.md`, `CONTRIBUTING.md`, …) point to the `v1-dev` line: GitLab `v1-dev`, `https://tadah.readthedocs.io/v1-dev/`. They pointed to `develop`.
- **`Context` stores values losslessly.** `add()`, `addInternal()` and the derived `RCUT2BMAX`/`RCUTMBMAX`/`RCUTMAX` keys used 18 fixed decimals: values below 5e-19 became 0 and small values lost digits on every add. `get<double>()` now returns the bit-identical value. The `Context` layout changed: rebuild LAMMPS (ML-TADAH embeds CORE) together with `tadah`.
- **`NUMERIC` defaults to 18 (was 12), and in potential and dataset files it means significant digits (`%.{N}g`).** 18 reads back bit-identically. An explicit NUMERIC below 17 is honoured with a WARNING that names the fix (delete the NUMERIC line), and NUMERIC is never written into a potential. Loaded values are never limited by NUMERIC. Other outputs (predictions, analysis tables) keep their meaning but are wider by default.
- Floating-point `std::to_chars` is required (libstdc++ >= 11, libc++ >= 14).
- **A `Matrix3d` no longer converts to a `Vec3d`.** `Vec3d`'s converting constructor, assignment, `+=` and `-=` took any indexable type; a `Matrix3d` (or any `Matrix_Base`) is now rejected at compile time, because its `operator[]` indexes the column-major storage, so elements 0..2 are column 0 — for a `Structure::cell` (a0x, a1x, a2x), not a lattice vector. Read a row or column with `row()`/`col()`. The scalar operators of `Matrix3d` (`s * m`, `m / s`, `*=`, `/=`) and `Vec3d` (`v * s`, `v / s`) take arithmetic scalars only (`A * B` of two matrices resolved to the scalar template and failed inside it). `Matrix_Base` and `Matrix3d` document `operator()(row, col)`, the column-major storage, `load()`'s row-major input (so a cell loads as a0x a0y a0z a1x …) and a cell's rows as lattice vectors; the swapped `row()`/`col()` comments are corrected. Tests: `test_maths.cpp`.

### Deprecated
- `MPIWPCKG`, `MBLOCK` and `NBLOCK`, the keys of the legacy MPI training build removed in 1.6.0. Configuration and potential files that contain them still load, with a warning on standard error, and the values are ignored. The keys lost their default values, so a Context never holds them and a newly written potential never contains them.

### Removed
- The `TADAH_BUILD_MPI` branch of `Logger::log` (an `MPI_Comm_rank` prefix). The flag was defined for MLIP and HPO but not for CORE and MODELS, so the two sides compiled different `Logger::log` bodies (an ODR violation).

### Fixed
- **199 of the 249 unit tests never ran under CTest.** The test name `histogram fixed-bin counts samples in [low, high)` has an unbalanced `[`, and the vendored Catch discovery script split the test listing through a CMake list, so that name and the 198 listed after it became one CTest entry. It matched no test case and still passed. With cmake-tools' discovery every test case is registered exactly once and an entry that matches nothing fails (`--warn NoTests`); all 249 run and pass. The explicit `core_pc_dataset_indices` entry, a workaround for this defect, is removed (its two cases are discovered).
- A `CoreUserConfigParser::parse` that threw (an invalid key or value, a missing `CONFIG` file) left the parser's recursion depth raised, so the next parse on that thread was treated as nested and did not reset its `CONFIG` chain. An RAII scope restores the depth on every exit.
- `is_number()`, `Checkpoint::get_dbl()` and the blueprint validator's long-line fast path accept subnormal values, which the lossless writers produce (`1e-310`). `is_number()` rejected them, so the HPO WARM reader shifted every later dimension of the key; a checkpointed subnormal read back as missing; and the validator fell back to its slow regex path. Overflow is still rejected.
- A potential written with a low explicit NUMERIC (1–5, 10, 11, 15 or 16) rendered the `DBL_MAX` `NSTDEV` sentinel of a constant descriptor column as text that overflows (`1.8e+308`), and the file could not be loaded again. Such a value is now truncated toward zero (`1.79e+308`).

## [1.3.0-beta.1] — 2026-05-20

First public beta of the Tadah! framework. CORE consolidates the blueprint, configuration, and registry layers and introduces the long-running-job infrastructure (checkpoint + signal handlers) used by HPO.

### Added
- `RCUTENV` blueprint key — envelope cutoff for the new `DM_mBlipEnv` descriptor.
- Load-time data-transform and filter blueprint keys: `LSCALE` / `NO_LSCALE`, `ESHIFT` / `NO_ESHIFT`, `ESHIFT_ATOM`, `ESHIFT_DBATOM`, `EWEIGHT_TEMP`, `EFILTER`, `FFILTER`, `WDBFILE` / `WDBFILE_AUTO`, `ZERO_COM_FORCE`. These are applied during dataset load before training and persisted into `pot.tadah` for prediction round-trip.
- Per-species intercept layout in the blueprint schema (`bias` key now documents the one-hot intercept column behaviour required when `NORM=true` with `MODEL=BF_Linear`).
- Checkpoint and signal-handler infrastructure for long HPO runs.
- Container-style `begin()` / `end()` iteration on `Config`.
- `TADAH_ENABLE_ASAN` CMake option for AddressSanitizer builds.
- Single-source-of-truth versioning: `project(... VERSION ...)` is now wired from `blueprint/blueprint_tadah.toml` via the `tadah_read_version_from_blueprint()` helper in `cmake-tools`.
- **Bound-validation primitives**: blueprint adds `AUDIT` (off / warn / error; default off), `AUDIT_SAMPLE` (NN-sweep cap, default 256; `0` = full DB), `HEALTH_LOG` (per-iter monitor verbosity), and the analysis subcommands `TASKS.analysis.{dataset_stats, suggest_bounds, check_bounds}`. `Registry` exposes `view()` and `names()` so the audit can enumerate registered descriptors without instantiating them.

### Changed
- C++ standard upgraded from C++14 to **C++17**. A C++17 compiler is now required.
- Blueprint key casing: `atom` → `ATOM` (consistency with the rest of the schema; case-sensitive parsers will need to update).
- `TYPEMB` value-type regex generalised to accept the additional spherical-harmonics-order parameter; existing 2-UINT `TYPEMB DM_<name> <mu> <nu> <El1> <El2>` lines still parse, and the new 3-UINT example form `TYPEMB DM_<name> <l> <mu> <nu> <El1> <El2>` is documented.
- `WATOM` blueprint type/handling corrected; bundled `DM_*` examples updated to match.
- `THRESHOLD` lost its top-level default (was `1e-6`); the per-task `[TASKS.data.balance.keys.threshold]` default tightened from `["1e-1", "2e-2", "3e-3"]` to `["1e-4", "1e-5", "1e-6"]`. **This changes `tadah data balance` results when the user does not pass `THRESHOLD` explicitly.**
- `Context` output formatting improvements.

### Fixed
- `Registry` static-initialisation order across translation units — descriptors / cutoffs / models registered in different `.cpp` files no longer race the factory map at first use.

### Internal
- Substantive README rewrite (Session B).
- Community / governance pointer files (CONTRIBUTING / CITATION / SECURITY / CoC).
- CI/CD: lint stage (codespell) and tag-gated release-tarball stage added; `.gitignore` extended.
- Test build routed through `cmake-tools/cmake/TadahTesting.cmake` helpers (`tadah_declare_testing` / `tadah_add_tests`); replaces the hand-rolled `BUILD_TESTING` setup. Fixes a silent test-suite-disable on a bare reconfigure where the previous code captured `BUILD_TESTING` before the cache entry existed and FORCE-restored an empty value.

## [1.2.0] and earlier (condensed)

The `v1.0.0` → `v1.1.1` releases were the project's "internal playground" era. CORE was bootstrapped as the central blueprint + config + registry layer for the Tadah! framework, with the blueprint TOML schema iterating ad hoc across releases (typo fixes, type corrections, and key additions for descriptor and cutoff parameters). The blueprint TOML version was rolled to `1.2.0` during this period but no `v1.2.0` git tag was ever pushed; consider any release before `1.3.0-beta.1` undocumented in the modern Keep-a-Changelog sense.
